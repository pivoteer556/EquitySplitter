Amendment 2026-11-09 (`BACKLOG.md` 2l step 3, enrolment at first sign-in for officers): `POST /auth/login` for an officer with NO confirmed authenticator now returns `200 {userType: "institution_user", enrolmentRequired: true, challengeToken}` and no access token. The challenge is a stateless 5-minute JWT with purpose `enrolment_challenge`, distinct from step 2's `login_challenge`; neither works as an access token or as the other. New `POST /auth/login/totp/enroll-start {challengeToken}` returns `{secret, otpauthUri}` (replacing a pending unconfirmed credential) and `POST /auth/login/totp/enroll-confirm {challengeToken, code}` returns the normal login response (sets `confirmedAt` and `lastUsedStep`, resets the limiter on the finished sign-in). A wrong code, bad or expired token, or an already-confirmed officer is `401 Invalid credentials` and wrong codes (and an already-enrolled officer on `enroll-confirm`) count in the shared `login` bucket, a bad token does not (no email to key on); a malformed code is 422. `POST /auth/institution/login` is REMOVED (404) because it returned a token on the password alone, bypassing both factors; the bearer endpoints `/auth/institution/totp/enroll` and `/confirm` remain. The login page has an enrolment step (secret as text, otpauth link, code field). Planned, not built: user and owner credentials, recovery codes, the admin role, reset, a back/restart control, a QR code, and a 429 message in the UI. No schema change. The Feature 2 change log row for this is added with the docx edit in the same commit.

Amendment 2026-11-09 (`BACKLOG.md` 2l step 3b, one-time recovery codes for officers): new table `recoveryCodes` (migration 0012: `id`, `institutionUserId` FK to `institutionUsers` ON DELETE CASCADE and indexed, `codeHash`, `usedAt` nullable, `createdAt`). Only hashes are stored: HMAC-SHA256 (hex) keyed by an HKDF of `JWT_SECRET_SEED` with its own label, so rotating the seed also invalidates unused codes (as it already does for stored authenticator secrets). `POST /auth/login/totp/enroll-confirm` now also returns `recoveryCodes` (exactly 8, format `XXXXX-XXXXX`, alphabet `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, about 49.5 bits each) on the first successful confirmation only; they are shown once and cannot be retrieved again. `POST /auth/login/totp` now accepts in `code` either the 6-digit authenticator code or a recovery code (case, spaces and the dash are ignored; any other shape is 422); a valid unused code returns the normal login response and is consumed, with a conditional UPDATE so two concurrent requests cannot spend one twice. A wrong or already-used recovery code is the same `401 Invalid credentials` as a wrong authenticator code and counts in the shared `login` bucket (5 failures per 60 s per IP+email, the 6th is 429 with `Retry-After`); a success resets the bucket. A recovery code is refused at `enroll-confirm` (that field stays exactly 6 digits, 422) and cannot enrol an officer or skip the second factor. The login page shows the codes once after enrolment with a save-now message and a Continue button (no navigation until Continue) and its second-step field accepts a recovery code. Known limits: officers who enrolled through the bearer endpoints `/auth/institution/totp/enroll` and `/confirm` (204) got no codes, and neither did officers who enrolled before this change (regeneration is not built, so they have none); the codes are on screen once and a reload on that screen loses them (the session stays valid); a 10-character code is ~49.5 bits, acceptable only behind the limiter; no admin reset. Planned, not built: regenerating codes, user and owner credentials and codes, the admin role, reset. The Feature 2 change log row for this is added with the docx edit in the same commit.
Amendment 2026-11-09 (`BACKLOG.md` 2l step 3c, regenerating recovery codes): new endpoint `POST /auth/institution/totp/recovery-codes` (officer bearer token, body `{code}` exactly 6 digits; response `{recoveryCodes}`, 8 codes). It needs a CURRENT authenticator code; a recovery code is refused (422), so a stolen session or a spent code alone cannot mint new ones. The code is replay-protected through the credential's `lastUsedStep`. A wrong or replayed code, or an officer with no confirmed authenticator, is the generic `401 Invalid credentials`, counted in the shared `login` bucket (5 failures per 60 s per IP+email, the 6th is 429 with `Retry-After`); success resets it. On success ALL the officer's old rows in `recoveryCodes` (used and unused) are deleted and 8 new ones inserted in one transaction, so a failure leaves the old set and every earlier code is dead. No migration and no schema change. This is how officers who enrolled before 3b, or through the bearer endpoints `/auth/institution/totp/enroll` and `/confirm`, can obtain codes. Frontend: `ApiService.regenerateRecoveryCodes(code)` existed but NO screen called it at that point (the `/security` page is built since 2026-11-09, see the next amendment). Planned, not built at that point: a signed-in officer settings or security page to use it (built, see the next amendment), keeping the codes across a reload, an admin reset, the ADMIN role, user and owner credentials. The Feature 2 change log row for this is added with the docx edit in the same commit.
Amendment 2026-11-09 (`BACKLOG.md` 2l step 3d, the officer security page): the frontend now has a screen for regenerating recovery codes. Route `/security` (guarded by `officerGuard`, so a signed-out visitor is rerouted to `/login`), reached from the `Security` link (`#security-link`) in the workbench header. The page has one field (`#security-code`, exactly 6 digits) and a submit button; it calls `ApiService.regenerateRecoveryCodes(code)` (`POST /auth/institution/totp/recovery-codes`, unchanged) and shows the 8 new codes once (`#security-recovery`, `#security-codes`) with the same save-now wording as the enrolment display. A wrong or replayed code shows `Incorrect or expired code. Check your authenticator app and try again.` (`#security-error`) and keeps the session. No schema or migration change (one backend auth fix, below). Auth behavior change in the frontend interceptor: `/auth/institution/totp/recovery-codes` was added to `TOKEN_LINK_PATHS`, because the interceptor treated any 401 as a lost session (cleared the tokens and redirected to `/login`), so a mistyped code signed the officer out; the trade-off is that a genuinely expired session on `/security` shows the same incorrect-or-expired message instead of redirecting, and the guard catches the next navigation. The codes markup and CSS were COPIED from the login page's enrolment display, not shared (it could later become a shared component). Known limits: the codes live in memory only, so a reload loses them; a 429 shows the generic rate-limit sentence, not the `Retry-After` time; e2e covered the happy path and a wrong code, not a replayed code or the rate limit. Auth behavior change in the backend (found by the e2e, same commit): `POST /auth/institution/totp/recovery-codes` no longer rotates the officer's stored session token before the code is checked. It now uses `require_institution_user_unrotated` (authenticates, does not rotate) and rotates only after success: a success still returns `X-Refreshed-Token`; a wrong or replayed code (401) or a 429 leaves the stored token unchanged, so the browser's token stays valid. Before the fix a rejected code rotated the token while the 401 carried no `X-Refreshed-Token`, so the next call failed with `401 Token no longer active`. The 401/429/limiter behavior and the response are otherwise as in the 3c amendment. PLANNED, NOT FIXED at that point: the same rotate-before-validate hazard on `POST /auth/institution/totp/confirm` (400/429) and `/totp/enroll` (409), and possibly on ordinary 4xx after the rotating dependencies and on revoke (`BACKLOG.md` section 6); `/totp/enroll` and `/confirm` are fixed since the 2026-11-10 amendment below, the rest is still PLANNED, NOT FIXED. Planned, not built: keeping codes across a reload, a `Retry-After` message, an admin reset, the ADMIN role, user and owner credentials, a back control, a QR code.
