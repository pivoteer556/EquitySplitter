Also built (2026-11-09 amendment, `BACKLOG.md` 2n): `POST /auth/login` is now the single sign-in for every account: it tries the user account (owner, buyer, platform admin) first and then the officer account, and returns the token plus `userType` (`user` or `institution_user`), `isPlatformAdmin`, and for officers `role` and `institutionId`; one rate-limit bucket per IP+email (`POST /auth/institution/login` was shared with it then and is REMOVED since 2026-11-09, see the last amendment below). The Feature 2 change log row for this is added with the docx edit in the same commit. Also built (2026-11-09 amendment, `BACKLOG.md` 2l step 2): `POST /auth/login` for an officer with a CONFIRMED authenticator credential returns `{userType: "institution_user", secondFactorRequired: true, challengeToken}` instead of an access token, and the new `POST /auth/login/totp` (`challengeToken`, 6-digit `code`) returns the normal login response. The challenge is a stateless HS256 JWT with `userType` `login_challenge` (5 minutes) that every auth dependency rejects; a wrong or replayed code or a bad challenge is `401 Invalid credentials`, a malformed code is 422; failures share the `login` rate-limit bucket and a correct password alone does not reset it. Planned, not built (as of that amendment): enrolment at first sign-in, recovery codes, user-side credentials (owners and buyers), the admin role, reset, and a back control on the code form; enrolment at first sign-in and its UI are built since the next amendment. The Feature 2 change log row for this is added with the docx edit in the same commit.

Amendment 2026-11-09 (`BACKLOG.md` 2l step 3, enrolment at first sign-in for officers): `POST /auth/login` for an officer with NO confirmed authenticator now returns `200 {userType: "institution_user", enrolmentRequired: true, challengeToken}` and no access token. The challenge is a stateless 5-minute JWT with purpose `enrolment_challenge`, distinct from step 2's `login_challenge`; neither works as an access token or as the other. New `POST /auth/login/totp/enroll-start {challengeToken}` returns `{secret, otpauthUri}` (replacing a pending unconfirmed credential) and `POST /auth/login/totp/enroll-confirm {challengeToken, code}` returns the normal login response (sets `confirmedAt` and `lastUsedStep`, resets the limiter on the finished sign-in). A wrong code, bad or expired token, or an already-confirmed officer is `401 Invalid credentials` and wrong codes (and an already-enrolled officer on `enroll-confirm`) count in the shared `login` bucket, a bad token does not (no email to key on); a malformed code is 422. `POST /auth/institution/login` is REMOVED (404) because it returned a token on the password alone, bypassing both factors; the bearer endpoints `/auth/institution/totp/enroll` and `/confirm` remain. The login page has an enrolment step (secret as text, otpauth link, code field). Planned, not built: user and owner credentials, recovery codes, the admin role, reset, a back/restart control, a QR code, and a 429 message in the UI. No schema change. The Feature 2 change log row for this is added with the docx edit in the same commit.
